# ライブラリの強制再読み込み（バックエンド） 仕様書

## 1. 概要

Eagle のメニュー「キャッシュをクリアしてライブラリを再読み込み」と同等の処理を、
スマホから HTTP 経由で実行できるようにする。プラグイン側は
**ライブラリキャッシュファイルの削除 → `eagle.library.switch()` で開き直し → 完了の監視**を担い、
進行状態をエンドポイントで返す。

## 2. 背景・目的

NAS 上のライブラリを複数端末の Eagle で開いていると、他端末での操作（ゴミ箱移動など）が
反映されないことがある。Eagle 本体のメニューから強制再読み込みすれば直るが、
Mobile Eagle を使っているときは Eagle の画面が手元に無い。スマホから実行できるようにする。

プラグインから Eagle 本体の再読み込み処理を直接呼ぶ手段は無い
（`ipcRenderer` に触れられない。knowledge.md に詳細）。
そこで本体の `reloadWithoutCache()` の中身を読み、**キャッシュファイルの削除と開き直しを自前で再現する**。
実機（Eagle 4.0.0 / Windows、2.6 万件、NAS 経由）で、古い状態が正しい状態に揃うことを確認済み（2026-09-28）。

## 4. 機能要件

### 4.1 再読み込みの処理

1. **状態を `running` にする（開始時刻を記録）。** 以降の処理は await を挟むため、
   先に `running` にしないと、その間に来た 2 本目の要求も開始してしまう
2. キャッシュファイルのパスを求める：
   `path.join(eagle.app.userDataPath, 'library-caches', hashFnv32a(eagle.library.path) + '.txt')`
   - `hashFnv32a` は Eagle 本体と同じ FNV-1a 32bit（8 桁の hex、ゼロ埋め）。
     計算式は [library-reload.js](../../../plugin/js/library-reload.js) の `hashFnv32a()`
3. **キャッシュファイルが無い、またはサイズ 0 なら実行しない**（`error`、理由 `busy`）
   - キャッシュファイルが無いのは、Eagle が再構築の途中にいるとき（前回の `timeout` の後も含む）。
     **再構築中に `switch` を呼ぶと読み込みが並行して走り、一時的にライブラリが空になる**（knowledge.md。Windows で発生）
4. **未保存の変更を書き出させるため、まず `switch` だけを呼ぶ**（1 回目）
   - `switch` は開き直す前にキャッシュを保存し、メモリ上に未保存の変更があれば書き出す。
     これを済ませずに削除すると、削除直後に古いデータで書き戻され、再構築されない（knowledge.md。Mac で再現）
   - **`onLibraryChanged` の発火を待つ**（読み込み完了の直後に発火することを確認済み。Windows でも約 3.4 秒）。
     60 秒待っても発火しなければ `error`（理由 `switch_failed`）
   - 例外、または `true` 以外が返ったら `error`（理由 `switch_failed`）
5. キャッシュファイルを削除する
   - 削除しようとした時点で消えていた（`ENOENT`）場合は「無し」として続行する
   - それ以外の失敗（ロック中など）は `error`（理由 `delete_failed`）。`switch` は呼ばない
     （古いキャッシュを読み直すだけで意味がないため）
6. `eagle.library.switch(eagle.library.path)` を呼ぶ（2 回目。未公開 API。実機で `true` が 23ms で返った）
   - 例外、または `true` 以外が返ったら `error`（理由 `switch_failed`）
7. **`onLibraryChanged` の発火で完了を判定する**。発火したらキャッシュファイルを確認する
   - ファイルがあり、サイズが 0 より大きい → 8 の書き戻し判定へ
   - ファイルが無い、またはサイズ 0 → `running` のまま次の発火を待つ
     （読み込みが並行した場合、先に終わる方は 0 件・0 バイトになり、後の方で正しく上書きされる。knowledge.md）
8. **書き戻しの判定**：キャッシュファイルの更新時刻と発火時刻の差を見る
   - 再構築した場合、ファイルは発火の約 30ms 前に書き出される（Mac / Windows で確認）
   - 書き戻された場合、ファイルは削除直後に書き出され、その後キャッシュの読み込み（Mac で 0.3 秒、Windows で 2.5 秒以上）
     を経てから発火する
   - 差が **1 秒以内なら `done`**、それより大きければ `error`（理由 `not_rebuilt`）
9. 開始から **15 分**経っても 7〜8 で `done` にならなければ `timeout` にする

- 4 と 5 の間に新たな変更（画像の追加など）が入ると、2 回目の `switch` でも書き戻しが起きる。
  8 で検出して `not_rebuilt` を返す（自動では再実行しない。ユーザーがもう一度実行する）
- タイムアウトは、状態を返すとき（`getStatus()`）に経過時間で判定する。
  完了は `onLibraryChanged` で判定するので、非表示ページのタイマー精度には左右されない
- `onLibraryChanged` のリスナーは `library-reload.js` で独自に登録する（`main.js` の既存リスナーと共存できることを確認済み）。
  `running` 中でないときの発火は無視する
- **`mtime.json`（ライブラリ直下）は触らない。** 本体の処理では削除・再作成しているが、
  NAS 上で全端末が共有するファイルのため。触らなくても直ることを確認済み
- `switch` によって `onLibraryChanged` が発火し、既存処理（[main.js](../../../plugin/js/main.js)）が
  圧縮画像キャッシュを全削除し、同じパスでも「ライブラリを切り替えました」とログに出る。
  実害はない（再生成されるだけ）ため、この仕様では抑止しない

### 4.2 状態

プラグインのメモリ上に 1 つだけ持つ（永続化しない）。

| state | 意味 | 遷移先 |
| --- | --- | --- |
| `idle` | 一度も実行していない | → `running` |
| `running` | 開始処理中、または再構築中（`onLibraryChanged` 待ち） | → `done` / `timeout` / `error` |
| `done` | 完了 | → `running`（再実行） |
| `timeout` | 15 分以内に完了しなかった | → `running`（再実行） |
| `error` | 実行できなかった・失敗した（理由は 4.3） | → `running`（再実行） |

- 開始処理の失敗は `running` から `error` へ移る（4.1 の手順 1 で先に `running` にしているため）
- `done` / `timeout` / `error` は次の実行まで保持する（遅れてポーリングした端末も結果を見られるように）
- **`running` 中の再実行要求は新たに開始せず、現在の状態をそのまま返す**（二重実行の防止）
- 実行中に `eagle.library.path` が開始時と異なる値になったら、監視を止めて `error`（理由 `library_changed`）にする
  - 再構築中に `library.path` が一時的に別の値（null など）を返さないかは未検証。
    コミットポイントで確認し、返すなら判定を見直す

### 4.3 理由コード

`error` / `timeout` のときは、画面に出す文章ではなく**理由コード**を返す。
文言はフロントエンドが i18n で持つ（英語 UI にも対応するため）。

| reason | 状態 | 意味 |
| --- | --- | --- |
| `busy` | `error` | キャッシュファイルが無い（Eagle が再構築中）。しばらく待ってから再実行する |
| `delete_failed` | `error` | キャッシュファイルを削除できなかった |
| `switch_failed` | `error` | `switch` が例外を投げた、`true` 以外を返した、または 1 回目の読み込みが 60 秒で終わらなかった |
| `not_rebuilt` | `error` | 削除直後に未保存の変更が書き戻され、再構築されなかった。もう一度実行する |
| `library_changed` | `error` | 実行中にライブラリが切り替わった |
| `timeout` | `timeout` | 15 分以内に完了しなかった |

### 4.4 ログ

ステータスウィンドウのログ（`ME.logger`）に次を記録する。

- 開始：`ライブラリの再読み込みを開始しました: <ライブラリパス>`
- 完了：`ライブラリの再読み込みが完了しました（<所要秒>秒）`
- タイムアウト・エラー：理由コードと例外メッセージを記録する

`GET /reload_library_status` のリクエストはログに記録しない（ポーリングで直近 200 件を埋めてしまうため。`server.js` の `QUIET_PATHS`）。

タイムアウト・エラーは**軽微エラー扱い**（ログのみ。ダイアログは出さない。coding.md 9 章）。
機能としては失敗だが、スマホ側に結果が表示されるため、Eagle 側で重ねて知らせる必要はない。

## 6. HTTP エンドポイント

どちらも `/api/eagle/*` 配下なので**認証が必要**（auth.md 5.3。localhost は免除）。

### 6.1 `POST /api/eagle/reload_library` — 再読み込みを開始する

- リクエストボディ：なし
- **状態を `running` にした時点ですぐに応答する。** 開始処理（4.1 の 2〜6）は応答の後に非同期で進める
  （1 回目の `switch` の後に待ちが入り、NAS 経由では数秒以上かかり得るため。HTTP を待たせない）
- レスポンス：6.3 の状態オブジェクト
  - 開始した場合も、すでに `running` だった場合も `200`
  - 開始処理の失敗は、後続の `GET /reload_library_status` で `state: 'error'` として見える
  - **失敗も `200` + `state: 'error'` で返す**（状態取得が開始処理の失敗より後になる場合も同じ）。base.md 6 章の共通仕様
    （エラーは `status: 'error'` + 4xx/5xx）の例外になる。理由：フロントエンドの `requestJson` は
    `status: 'error'` を例外にするため、失敗を「状態」として受け取れなくなり、表示が 2 系統に分かれる。
    ここでの失敗は通信の失敗ではなく処理結果なので、状態として返す

### 6.2 `GET /api/eagle/reload_library_status` — 状態を返す

- レスポンス：6.3 の状態オブジェクト
- 副作用は 4.1 のタイムアウト判定のみ（状態を進めるだけで、Eagle には何もしない）

### 6.3 状態オブジェクト

```json
{
  "status": "success",
  "reload": {
    "state": "running",        // 'idle' | 'running' | 'done' | 'timeout' | 'error'
    "elapsedMs": 83000,        // running: 開始からの経過 / done 等: 所要時間 / idle: 0
    "timeoutMs": 900000,       // 15 分（フロントエンドの表示・判定用）
    "reason": null             // error / timeout のときの理由コード（4.3）
  }
}
```

- 状態は `data` ではなく **`reload` キー**で返す（`/api/version` が `version` キーで返すのと同じ流儀。
  一覧系の `data` とは性質が違うため）
- 経過時間は**サーバーで計算した値**を返す（端末の時計のずれに影響されないため）
- ライブラリパスやキャッシュファイルのパスは**返さない**（フロントエンドに不要。個人のパスを出さない）

## 9. エッジケース・エラー処理

| ケース | 挙動 |
| --- | --- |
| 開始時にキャッシュファイルが無い / サイズ 0 | `error`（`busy`）。`switch` は一度も呼ばない（再構築中の `switch` はライブラリを一時的に空にするため） |
| 1 回目の後、削除時に消えていた（`ENOENT`） | 「無し」として続行し、2 回目の `switch` を呼ぶ |
| 削除に失敗（`ENOENT` 以外） | `error`（`delete_failed`）。`switch` は呼ばない |
| `switch` が例外 / `true` 以外 / 1 回目の読み込みが 60 秒で終わらない | `error`（`switch_failed`） |
| 削除直後に書き戻された（4.1 の 8） | `error`（`not_rebuilt`） |
| 完了の発火でキャッシュファイルが 0 バイト | `running` のまま次の発火を待つ（4.1 の 7） |
| 実行中（開始処理中を含む）に再実行要求 | 何もせず現在の状態を返す（4.2） |
| 実行中にライブラリが切り替わった | `error`（`library_changed`） |
| 15 分で完了しない | `timeout`。監視を止める。Eagle 側の処理は止めない（止める手段がない） |
| `timeout` の後に再実行 | Eagle 側の再構築がまだ続いていればキャッシュファイルが無いので `busy` で断る。終わっていれば通常どおり実行する |
| 実行中にプラグインを再読み込み / Eagle を再起動 | 状態は失われ `idle` に戻る。フロントエンドはこれを検出して終了扱いにする（frontend 側 9 章） |
| 再構築中の `/list` などのリクエスト | 通常どおり応答する。**完了までは古いデータが返る**（検証済み）。フロントエンドは完了後に読み直す |
| Eagle のアップデートでキャッシュの場所・名前が変わった | 開始時にファイルが見つからず `busy` になる。フロントエンドは、繰り返し `busy` になるなら Eagle 本体のメニューから実行するよう案内する |

## 10. セキュリティ

- 認証必須（`/api/eagle/*`）
- リクエストから受け取る値は無い。削除するパスはサーバー側で算出した 1 ファイルのみ
  （`library-caches` ディレクトリ外のファイルを消すことはない）
- 開始処理の前に `running` にするため、連打による多重実行は起きない
- キャッシュファイルが無い間は実行しないため、再構築中の `switch`（ライブラリが一時的に空になる）は起きない
- **既知の割り切り**：パスワード未設定のときは、他サイトからのフォーム POST でも実行できてしまう
  （ボディ不要のため。パスワード設定時は Cookie の `SameSite=Strict` で防げる）。
  既存の `move_to_trash` なども同じ条件であり、この機能で新たに生じる問題ではないため、対策しない

## 11. スコープ外

- `mtime.json` の削除・再作成（4.1）
- 再構築の中止（Eagle 側に手段がない）
- 進捗率の表示（Eagle 側に取得手段がない。経過時間のみ）
- ステータスウィンドウからの実行ボタン（Eagle の画面が手元にあるなら本体メニューを使えばよい）
- 他ライブラリの強制再読み込み（開いているライブラリのみ対象）
