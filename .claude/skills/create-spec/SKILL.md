# create-spec — 機能仕様書の作成

大きな機能（HTTP サーバー、API エンドポイント群、ステータスウィンドウ、フロントエンドの移植など）の
実装に着手する前に、その機能の詳細仕様書を起こすスキル。
仕様書は `.claude/specs/<機能名>.md` に保存する（既存の `plugin-test.md` `coding.md` と同じ場所）。

**このプロジェクトでは、大きな機能は必ず仕様書を起こしてから実装に入る。**
本スキルは仕様書の作成までを担当し、実装コードは書かない。

## 前提

- プロジェクトの目次は **`CLAUDE.md`**。全体方針・検証結果は **`.claude/概要.md`** を「唯一の正」とする。
  本スキルが作るのは個別機能の詳細仕様であり、これらと矛盾してはならない。
  整合しない点が出たら、どちらを直すかユーザーに確認する。
- コーディング規約は `.claude/specs/coding.md` に従う。
- **Eagle Plugin API の実挙動は `.claude/specs/plugin-test.md` を正とする。**
  公式ドキュメントと食い違う項目が複数確認されているため、**公式ドキュメントの記述を根拠に設計しない。**
- 実装の知見・落とし穴は `.claude/knowledge.md` に蓄積されている。着手前に必ず読む。

## 手順

### 1. 対象機能の確認

- 機能の名前・目的・スコープをユーザーにヒアリングする。
- 保存ファイル名を決める（内容を表す kebab-case の英数字。例：
  `.claude/specs/http-server.md`、`.claude/specs/status-window.md`）。
- 既存の `.claude/specs/` に同名・類似の仕様が無いか確認する。

### 2. 既存ドキュメントの確認

- `CLAUDE.md`（目次）から関連ドキュメントをたどる。
- `.claude/概要.md` の「検証結果の要点」「実装時の留意点」を読み、矛盾・重複がないか把握する。
- `.claude/specs/coding.md` の規約（特に「6. Eagle プラグイン固有の規約」）を踏まえる。
- `.claude/specs/plugin-test.md` の検証結果を踏まえる。**確定した制約に反する設計をしない。**
  - ゴミ箱内アイテムは取得できない
  - `eagle.item.get()` に `orderBy` / `limit` / `offset` はない
  - `onPluginRun` は Eagle 起動時にも発火する
  - 画像読み込みは `fs`、変換は `OffscreenCanvas`
- `.claude/knowledge.md` に関連する落とし穴がないか確認する。
- 検証用プラグイン **`plugin-test/js/main.js`** に流用できる実装があるか確認する
  （`serveStatic()` / `startServer()` / `resolvePluginRoot()` / `compressItem()` / `listIpAddresses()` など）。

### 3. 移植元の確認

- 移植元の **Simple Eagle `/Volumes/D/works/simple-eagle`** の該当箇所を参照し、
  再現すべき挙動・API のインターフェースを把握する。
  - バックエンド：`index.py` / `modules/eagle_api.py` / `modules/util.py`
  - フロントエンド：`src/js/`（Vue 3 + TypeScript + Pinia + Tailwind）
- **推測で書かない。** Simple Eagle が Eagle Web API（`localhost:41595`）で行っていた処理を
  プラグイン API（`eagle.item` / `eagle.folder`）に置き換える際は、対応する API の実在を確認する。
- 挙動を変える場合は、その理由を仕様書に明記する。

### 4. 要件のヒアリング

- 仕様が曖昧な点は `AskUserQuestion` などで質問し、決め切る。
- どうしても未確定で残る論点は「オープン課題」として仕様書に記録する。

### 5. 仕様書ドラフトの作成

下記テンプレートに沿って `.claude/specs/<機能名>.md` を作成する。

- 既存 `.claude/specs/plugin-test.md` の文体・見出し記法（`## N. 見出し` 形式）に合わせる。
- 該当しないセクションは省略してよいが、**「実装ステップ」は必ず含める。**
- 文章・コメント・UI 文言はすべて日本語。インデントは 2 スペース。

#### コミットポイントの決め方

実装ステップは「📌 コミットポイント」で区切る。区切り方の目安：

- **Eagle にプラグインを読み込み直して動作確認できる単位**で区切る。
- 「HTTP サーバーが起動して `/ping` が返る」「API エンドポイントが 1 つ完成」
  「ステータスウィンドウの 1 項目が動く」など、レビューしやすい粒度にする。
- 依存方向に沿い、**プラグイン側の下位レイヤー（ユーティリティ / Eagle API ラッパー）
  → HTTP サーバー / API → フロントエンド** の順で下位から区切る。
- 粒度の目安は **2〜5 ステップに 1 回**。無コミットで 10 ステップ続くのも、
  1 ステップごとにコミットするのも避ける。

#### テンプレート

````markdown
# <機能名> 仕様書

## 1. 概要

<1〜3 文で機能の要約>

## 2. 背景・目的

<なぜこの機能が必要か。解決する課題。Simple Eagle からの変更点があれば理由も>

## 3. 関連ドキュメント

- 目次: `CLAUDE.md`
- 全体方針・検証結果: `.claude/概要.md`
- コーディング規約: `.claude/specs/coding.md`
- Eagle API の実挙動: `.claude/specs/plugin-test.md`
- 実装知見: `.claude/knowledge.md`
- <移植元 Simple Eagle の該当ファイル / 参照した Eagle API など>

## 4. 機能要件

<機能の振る舞いを箇条書き・表で具体的に。入力・出力・状態遷移を明記する>

## 5. 実行環境

<プラグイン側（Node.js が使える）か、フロントエンド側（ブラウザ）か、両方か。
 両方にまたがる場合は責務の分界点を明記する>

## 6. HTTP エンドポイント

<新規・変更するエンドポイント。パス / メソッド / リクエスト / レスポンス / 認証の要否。
 既存エンドポイントと衝突しないこと。該当しなければ「対象外」と明記する>

## 7. UI 仕様

<UI を伴う場合: ステータスウィンドウ、またはフロントエンドの画面構成・状態の見せ方。
 UI 変更が無ければ「UI 変更なし」と明記する>

## 8. データ構造・Eagle API の利用

<使用する Eagle API（eagle.item / eagle.folder など）と取得するプロパティ。
 新規・変更する TypeScript 型、Pinia ストアの状態。
 localStorage に保存するキーと値（既存キーと衝突しないこと）>

## 9. エッジケース・エラー処理

<異常系、境界値、fetch 失敗時の挙動、ユーザーへのエラー表示（重大/軽微の区別）。
 ライブラリ切り替え時の挙動。サーバー停止中の挙動>

## 10. セキュリティ

<LAN に公開される前提での考慮。認証の適用範囲。
 静的ファイル配信を伴う場合はトラバーサル対策。該当しなければ「対象外」と明記する>

## 11. スコープ外

<この仕様書で対応しないこと（将来対応を含む）。
 Eagle API の制約により実装できないこと（例: ゴミ箱閲覧）があれば明記する>

## 12. 実装ステップ

機能を上から順に実装する。各「📌 コミットポイント」は動作を確認できる区切りで、
ユーザーのレビュー後に `/step-commit` でコミットすることを想定している。

- [ ] 1. <作業内容（1 ステップ＝1 つの明確な成果物）>
- [ ] 2. <作業内容>

> 📌 **コミットポイント 1** — <この時点で確認できること。
> 例: プラグインを読み込み直すと HTTP サーバーが起動し `/ping` が返る>
> → ユーザーがチェック → `/step-commit` でコミット

- [ ] 3. <作業内容>
- [ ] 4. <作業内容>

> 📌 **コミットポイント 2** — <この時点で確認できること>
> → ユーザーがチェック → `/step-commit` でコミット

## 13. オープン課題

- [ ] <未確定の論点。確定したら本文へ反映する>
````

### 6. レビューの実施

作成したドラフトを **`spec-reviewer` エージェント** に渡してレビューさせる。
特に「Eagle Plugin API の検証済み制約への適合」を重点的に見てもらう。
指摘があればユーザーに提示し、反映の要否を確認する。

### 7. 提示と次のステップ案内

- 作成した仕様書のパスと概要をユーザーに日本語で提示する。
- 次のアクションを案内する：
  1. ユーザー自身が仕様書をレビューする。
  2. 指摘を反映して仕様を確定する。
  3. 確定後に実装へ着手する。実装中はコミットポイントごとにユーザーのチェックを受け、
     `/step-commit` でコミットする。
- **このスキルでは実装コードは書かない。** 仕様書の作成までで終了する。
