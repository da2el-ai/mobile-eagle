# Step 完了時のコミット支援

機能実装の区切り（仕様書の「📌 コミットポイント」）で呼び出されます。
以下の手順で knowledge の更新とコミットを支援してください。

## 前提

- **このプロジェクトはまだ Git リポジトリではない可能性がある。**
  `git rev-parse --is-inside-work-tree` で確認し、リポジトリでなければ
  「`git init` しますか？」とユーザーに確認する。**勝手に `git init` しない。**
- 知見の記録先は **`.claude/knowledge.md` の単一ファイル**（ディレクトリではない）。

## 手順

### 1. 変更内容の確認

```bash
git status
git diff
git log -5
```

を並列で実行し、変更の全体像を把握します。
`.gitignore` はこのスキルのコミット対象から除外する。コミットが必要な時はユーザー自身で行う。

### 2. 記録先の判断

ユーザーに **どこに記録するか** を確認します（候補を提示）：

- **`.claude/knowledge.md`** — 実装知見・落とし穴。新たに発見したトリックやハマりどころ。
  **特に Eagle Plugin API の挙動が公式ドキュメントと違った場合は必ず記録する**
- **`.claude/specs/<機能名>.md`** — 仕様書側に反映すべき決定事項。
  実装ステップのチェックボックス（`- [ ]` → `- [x]`）の更新もここで行う
- **`.claude/specs/coding.md`** — 今後も守るべき規約として一般化できるもの
- **`.claude/概要.md`** — プロジェクト全体の方針に関わる決定
- **どこにも書かない** — コミットメッセージで十分な内容

複数該当する場合はそれぞれに追記。

### 3. 記録内容の提案

ユーザーに **追記する文面の案** を提示します。原則：

- 日本語、簡潔に
- WHY と HOW（なぜそうしたか / どう実装したか）を含める
- WHAT（何を実装したか）はコミットメッセージで十分なので、knowledge には**実装上の発見・罠**だけを書く
- ファイルパス・関数名は具体的に
- **Eagle 固有の落とし穴は、後から「不要では？」と削除されないよう理由を厚めに書く**

ユーザーの確認を得てから書き込み。

### 4. コミット

ユーザーが「コミットして」と明示したらコミットします。**自動で勝手にコミットしない。**

コミット時は通常の Git コミット手順に従う：

- 機能単位でコミットを分ける（複数の独立した変更が混ざっていれば分割を提案）
- メッセージは日本語
- `feat:` / `fix:` / `refactor:` などの prefix を踏襲（`git log` で既存スタイルを確認）
- `Co-Authored-By` 行を付ける

### 5. INSTRUCTION.md のクリア確認

`.claude/INSTRUCTION.md` に内容があり、その指示が完了したと思われる場合、
**ユーザーに「INSTRUCTION.md をクリアしますか？」と確認**する（自動でクリアしない）。

## 注意

- `git add -A` / `git add .` は使わず、**変更ファイルを明示的に指定**する
- **`node_modules/` を絶対にコミットしない。** `plugin/node_modules/` と `plugin-test/node_modules/` が
  `.gitignore` に入っているか確認する。入っていなければ警告する
- フロントエンドのビルド成果物（`plugin/public/`）をコミットするかは方針を確認する
  （`.eagleplugin` の配布に必要なため、コミットする可能性が高い）
- `.bak` / `.DS_Store` / 検証用の一時ファイルを発見したら警告する
